A couple of notes on that Kafka block:

KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092 assumes your Spring Boot app runs on your host machine (not containerized yet), matching how you're already reaching Postgres/Elasticsearch via localhost. If you later containerize the app itself and put it in this same compose file, you'd add a second listener advertised as watchlog-kafka:9092 for container-to-container traffic.
Optional but genuinely handy for debugging: add a provectuslabs/kafka-ui container pointed at watchlog-kafka:9092 so you can visually inspect topics and messages instead of using the CLI.
How Kafka changes your ingestion flow
Instead of the Ingestion API writing straight into Elasticsearch, it now just publishes:

POST /api/logs → Ingestion API validates the request, then produces the log event onto a Kafka topic (e.g. log-events) via KafkaTemplate.
A separate @KafkaListener(topics = "log-events", groupId = "log-indexer") consumer reads off that topic and writes each event into Elasticsearch.
This decouples the two: if Elasticsearch is briefly slow or down, Kafka just holds the backlog instead of your ingestion endpoint timing out or dropping data, and you can scale up indexing throughput later by adding more consumer instances in the same group.

Time-series via TimescaleDB
Your metric_point(service_id, metric_name, timestamp, value) table lives in the same Postgres container now — you just enable the extension and convert the table into a hypertable after your JPA schema creates it:

sql
CREATE EXTENSION IF NOT EXISTS timescaledb;
SELECT create_hypertable('metric_point', 'timestamp');
Then your metrics-poller queries use time_bucket() for the bucketed aggregation your charts need:

sql
SELECT time_bucket('1 minute', timestamp) AS bucket, avg(value)
FROM metric_point
WHERE service_id = ? AND metric_name = 'cpu_usage'
GROUP BY bucket ORDER BY bucket;
One dependency update from earlier: spring-kafka moves from "optional, add later" to required now, since the ingestion path depends on it from the start.

Here's the full set of model classes, grouped by which module they belong to.

Registry (Postgres, JPA entities — central platform)

Project — id, name, createdAt
Service — id, project (FK → Project), name, baseUrl, healthPath, apiKey, createdAt
Health tracking (Postgres, JPA entity)

HealthCheckResult — id, service (FK → Service), timestamp, status (ServiceStatus enum), responseTimeMs
Metrics (TimescaleDB, JPA entity — the hypertable)

MetricPoint — serviceId, metricName, timestamp, value
Log storage (Elasticsearch, @Document class — not JPA)

LogDocument — id, serviceId, projectId, timestamp, level (LogLevel enum), logger, thread, message
Kafka message (plain POJO, the payload on the log-events topic)

LogEventMessage — same shape as LogDocument minus the ES-specific id; this is what the ingestion API produces and the consumer deserializes before writing to LogDocument
Shared enums

LogLevel — TRACE, DEBUG, INFO, WARN, ERROR
ServiceStatus — UP, DOWN, UNKNOWN
REST DTOs (request/response — keep these separate from the JPA entities above, don't expose entities directly over the API)

ProjectRequest / ProjectResponse
ServiceRequest / ServiceResponse — request excludes id/createdAt; response can also omit apiKey so it's never echoed back over the wire
LogIngestRequest — what the appender's HTTP POST body looks like: serviceId, timestamp, level, logger, thread, message
LogQueryRequest — filters for the query API: serviceId, level, from, to, keyword, page, size
LogQueryResponse — paginated wrapper: logs (List<LogDocument>), totalHits, page
HealthStatusResponse — current-status view for the dashboard: serviceId, status, lastCheckedAt, responseTimeMs
MetricQueryResponse — bucketed time-series for charts: serviceId, metricName, points (List<{timestamp, value}>)
Appender library (separate small project — the dependency each microservice pulls in)

LogEventPayload — mirrors LogIngestRequest's shape exactly, since this is literally what gets serialized and POSTed; keeping it a standalone class (not a shared dependency on the platform's DTO module) is deliberate — you don't want every microservice pulling in your whole platform's codebase just to log
One design note worth being explicit about: entities never leave the registry module directly — controllers map Project/Service entities to their Request/Response DTOs before returning anything. It's an extra mapping step, but it's what stops you from accidentally leaking the apiKey field or creating a tight coupling between your DB schema and your public API shape.
